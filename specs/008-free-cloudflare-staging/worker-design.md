# Hosted API execution design

**Decision:** Apply Spec 008's 2026-10-27 revision using a stateless API Worker and one SQLite-backed `DemoCoordinator` Durable Object for this demo's one global assistant queue, admission counters, and kitchen clock. This is a bounded coordination bottleneck, not a horizontally scaled production API. Ordinary menu, quote, checkout, and tracking logic executes in the Worker; it only asks the coordinator for admission. Both deployments use the same shared API handler and Supabase RPCs. Local Node development retains its HTTP server and timers.

## Ownership, execution, and privacy

- Every Worker isolate routes assistant submission, ticket polling/cancellation, and proposal confirmation to the same named coordinator (`public-demo-v1`). Requests and responses use Durable Object RPC; public callers cannot select an object identity or invoke internal alarm/admission methods.
- The coordinator owns the existing bounded assistant queue and proposal store in memory. No chat text, replies, cart snapshots, candidates, capabilities, or IP addresses are written to Durable Object storage. SQLite backing enables free-tier eligibility; only the hosted alarm timestamp is persisted there. Supabase remains the durable accounting and order authority.
- Eviction, deployment, or failure may lose transient content exactly as a local API restart did. A new coordinator receives a new process ID. Existing Supabase ticket ownership prevents re-creating/replaying lost jobs; requests recover through the existing localized expired/unavailable response and a new explicit user submission. Reserved/unknown charges and the global next slot remain in Supabase. Ordinary routing across Worker isolates does not lose affinity.
- An alarm wakes approximately every five seconds, advances the kitchen using the existing atomic RPC, and performs cleanup at most once per minute. It installs the next alarm before external I/O, so failures do not remove the recurring schedule. Existing Supabase five-minute cleanup remains an independent expiry safeguard. Alarm delivery may be delayed; overdue kitchen stages use existing catch-up semantics, not an exact timing guarantee.
- Each alarm also advances the assistant queue with execution attached to `ctx.waitUntil`; provider timeout remains eight seconds. No request/poll directly dispatches paid work. The queue's existing reentrancy guard and durable claim prevent concurrent dispatch. Five-second wake-ups replace the local one-second queue timer; estimates remain approximate, and a due dispatch may wait up to one wake-up under normal scheduling. Hosted delays may be longer. Cancellation and presence leases are rechecked before claims. No automatic provider retry is added, including on an alarm retry.
- All hosted admissions use one coordinator's bounded fixed-window counters, including the existing per-client limits and the 600/minute public-read and assistant-control limits. Only a SHA-256 IP digest is retained in volatile limiter memory for the window; expired entries are pruned, and new identities are rejected when the 10,000-entry capacity is full. These are global across concurrent Worker isolates, not durable across coordinator replacement. Replacement resets these short-lived abuse counters as an old Node restart did; it cannot reset durable order capacity, assistant pacing, or spending. This scope is explicit and is not authentication or a distributed attack guarantee.
- Secrets arrive through Cloudflare secret bindings, never `process.env` mutation. Runtime configuration is passed explicitly into each API instance/provider. Keep the real-assistant token accounting but bundle only its configured `o200k_base` ranks and initialize the tokenizer only on assistant work in the coordinator, where the documented CPU limit is 30 seconds. The ordinary Worker has the free 10 ms CPU limit.

## Capacity budget and deployment gates

Official references consulted on 2026-10-27: [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Durable Object limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [Durable Object pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/), [alarm lifecycle](https://developers.cloudflare.com/durable-objects/api/alarms/).

- Workers Free: 100,000 requests/day per account, 10 ms CPU per invocation, 128 MB memory, 3 MB compressed bundle. Existing static-only clients do not consume dynamic API invocation allowances for asset delivery.
- SQLite Durable Objects Free: 100,000 requests/day (including RPCs and alarms), 13,000 GB-s/day, 100,000 written rows/day, 5 million read rows/day, 5 GB stored data per account; 30-second CPU limit per request. No legacy KV-backed object, paid plan, container, or extra service is needed.
- Five-second alarms cost approximately 17,280 invocations and alarm writes/day. Each admitted public API request adds one coordinator RPC; assistant calls use their single coordinator RPC rather than a second limiter call. At 20,000 dynamic API requests/day, estimate 37,280 DO requests and 20,000 Worker invocations, before other account consumers/retries. Alarm set-on-construction adds a small restart allowance. A continuously active single 128 MB object uses approximately 10,800 GB-s/day (using 0.125 GB), below 13,000, but leaves limited account-wide duration headroom. Other objects, platform retries, and existing account usage must be considered.
- Polling is included in the request budget. One continuously foreground assistant poller at three-second intervals could use 28,800 requests/day; kitchen/tracking pollers also count. This free demo is not sized for unlimited concurrent viewers. Exhausted free quotas cause unavailable responses, not an authorized plan upgrade.
- No Supabase schema change is required for this design. Validate the existing project's grants, RPCs, cleanup schedule, and real ledger on deployment without replaying already-applied migrations. Existing database free-tier quotas still apply.
- Measure compressed bundle/startup, Worker and coordinator CPU/memory, outgoing calls, alarm activity, and representative journeys before reporting free-tier suitability. Record failures honestly in validation; do not weaken token accounting, drop features, or incur paid infrastructure to pass.

## Contract amendments

This design refines the original single-process implementation details in Specs 005/009 into a single hosted assistant owner. Their privacy, retention, queue, budget, idempotency, and confirmation contracts remain unchanged. Spec 006's local five-second worker becomes the hosted alarm described here. Spec 010's Worker non-goal no longer applies to this migration; its abuse controls retain the explicitly documented restart scope above. Spec 008 remains the deployment contract.
